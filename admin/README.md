# اتاق فرمان ابری رسانه میم

## ظاهر و مسیرها

- صفحهٔ `admin/` شامل ورود با نام کاربری و بازیابی رمز است.
- داشبورد RTL واکنش‌گرا با تم مشکی‌ـ‌طلایی سایت اصلی شامل منوی کناری، آمار واقعی محتوا، کارت پروژه با تصویر، اطلاعات تماس و امنیت حساب است.
- مسیرها نسبی‌اند و در GitHub Pages زیر `/TEST/` کار می‌کنند.
- صفحهٔ مرجع معرفی‌شده هنگام بررسی HTTP 403 داشت؛ این ظاهر یک طراحی اختصاصی است، نه بازسازی تأییدشدهٔ آن صفحه.

## Supabase

با انتخاب مالک، پروژهٔ موجود `ideh-pardazan` (`jmpwryddrxmuwzmbmhsb`) استفاده شده است. ساخت پروژهٔ جدا به محدودیت تعداد پروژه‌های رایگان برخورد کرد. جدول‌های IDEA تغییر نکرده‌اند.

جدول‌ها و توابع مستقل:

- `miim_content`: تک‌ردیف `main`، محتوای عمومی JSON، زمان ذخیره و نسخهٔ افزایشی.
- `miim_admins`: فهرست ایمیل مدیران؛ فاقد دسترسی عمومی یا دسترسی تغییر برای کاربران سایت.
- `miim_is_admin()`: بررسی سمت دیتابیس با `auth.uid()`، ایمیل واقعی `auth.users` و تأیید ایمیل؛ نه متادیتای قابل‌تغییر توسط کاربر.
- خواندن محتوا عمومی است. فقط مدیر تأییدشده حق UPDATE ستون data را دارد. INSERT/DELETE عمومی مجاز نیست.
- ایمیل اولیهٔ مدیر: `resane.miim@gmail.com`.
- شرط `revision` مانع بازنویسی بی‌خبرٔ ذخیرهٔ مرورگر دیگر می‌شود. در تعارض، پیش‌نویس حفظ می‌شود؛ کاربر با تأیید خود تازه‌سازی می‌کند.
- هش رمز/کلید خصوصی در محتوای عمومی ذخیره نمی‌شود. `authHash` قبل از خروجی و ارسال حذف و در DB نیز ممنوع شده است.
- فقط کلید **publishable** در کد مرورگر است. هرگز service-role یا secret key را در این ریپوزیتوری نگذارید.

فایل migration در `supabase/migrations/` و seed اولیه در `supabase/seed.sql` است. این فایل‌ها **روی پروژهٔ فعلی اعمال شده‌اند**؛ دوباره اجرا نکنید. seed فقط چهار نمونه‌کار را ذخیره می‌کند. سایر بخش‌ها از `data.json` پایه خوانده می‌شوند؛ اولین انتشار، سند کامل را ذخیره می‌کند.

## ورود مدیر

- نام کاربری مدیر `mojtaba` است. در لایهٔ اتصال Auth، این شناسه به حساب موجود `resane.miim@gmail.com` نگاشت می‌شود. ورود با ایمیل نیز برای سازگاری و تأیید رمز فعلی پشتیبانی می‌شود.
- رمز درخواستی مالک فقط سمت دیتابیس Auth به صورت bcrypt تنظیم شده و هیچ نسخه‌ای از آن در Git، کد مرورگر، مستندات یا دادهٔ عمومی وجود ندارد. حساب مدیر موجود با تأیید مدیریتی فعال شده است.
- نگاشت نام کاربری، مرز امنیتی نیست؛ رمز واقعی توسط Supabase Auth و مجوز مدیریت توسط RLS سرور بررسی می‌شود.
- برای بازیابی، می‌توان نام کاربری `mojtaba` را وارد کرد؛ لینک به ایمیل مدیر ارسال می‌شود.
- برای تغییر رمز، بخش «امنیت حساب» ابتدا رمز فعلی را با Auth دوباره بررسی می‌کند.

مسیر `https://miimdev.github.io/TEST/admin/` به allowlist تغییر مسیر Auth اضافه شده است. `site_url` و سیاست‌های ورود/ثبت‌نام پروژهٔ IDEA تغییر داده نشده‌اند. لینک تأیید/بازیابی به آدرس تولید برمی‌گردد، نه آدرس پیش‌نمایش. برای دامنهٔ سفارشی، allowlist و `redirectTo` در `lib/cloud.js` را به‌روزرسانی کنید.

ارسال ایمیل تابع محدودیت نرخ و تنظیمات SMTP همین پروژه است. اگر Supabase اجازهٔ ارسال به این ایمیل را نداد، SMTP مناسب را در داشبورد Supabase پیکربندی کنید؛ تأیید ایمیل را خاموش نکنید. تغییر رمز حساب فقط با درخواست صریح مالک و خارج از فایل‌های ریپوزیتوری انجام شده است؛ اعتبارسنجی رمز مرورگر هرگز با مقایسهٔ محلی انجام نمی‌شود.

## ذخیره و انتشار

«ذخیره و انتشار» محتوا را مستقیماً در Supabase ذخیره می‌کند. دیگر جایگزینی دستی `data.json` لازم نیست. صفحهٔ عمومی در هر بار بارگذاری دادهٔ ابری را می‌خواند؛ اگر اتصال قطع باشد، نسخهٔ `data.json` ریپوزیتوری را نمایش می‌دهد. پیش‌نویس‌های قدیمی localStorage هیچ‌وقت دادهٔ ابری را override نمی‌کنند. برای به‌روزرسانی تب عمومی باز، آن را بازخوانی کنید (تب‌های همین مرورگر از BroadcastChannel نیز مطلع می‌شوند).

«دریافت نسخهٔ پشتیبان» JSON فرم را بدون ذخیره/انتشار دانلود می‌کند. انتشار فقط وقتی موفق اعلام می‌شود که سرور ذخیره را تأیید کند. در قطع اتصال، خطای دسترسی یا تعارض نسخه، پیش‌نویس نگه داشته می‌شود. واردکردن فایل پشتیبان و بازگردانی تاریخچه تنها فرم را تغییر می‌دهد، نه سایت عمومی. برای اعمال آن‌ها باید «ذخیره و انتشار» را بزنید.

## توسعه و تست

```sh
npm ci
npm run build
npm test
python3 -m http.server 8000 --bind 0.0.0.0
# ترمینال دیگر:
npx playwright install chromium
npm run test:browser
```

باندل `vendor/miim-cloud.js` عمداً در Git است تا GitHub Pages بدون build و بدون CDN کار کند. تغییرات `lib/cloud.js` باید با دستور build بالا دوباره باندل شوند. فایل license کنار باندل نگه داشته شود.

تست مرورگر از API شبیه‌سازی‌شدهٔ Supabase استفاده می‌کند: هیچ ایمیل، کاربر آزمایشی یا تغییر محتوای واقعی ایجاد نمی‌شود. ورود از دکمهٔ هدر، نگاشت نام کاربری/مجوز مدیر، انتشار موفق و ناموفق، تعارض نسخه، بازیابی/تغییر رمز، خروج، نمایش عمومی و عرض موبایل تست می‌شوند. اعتبارسنجی زندهٔ دیتابیس جدا با connector انجام شد (RLS، دسترسی ستون‌ها و جلوگیری از UPDATE کاربر بدون عضویت).

## جلوگیری از کش نسخهٔ قبلی

بعد از هر تغییر CSS/JS، دستور `npm run build` را اجرا کنید. `scripts/version-assets.cjs` آدرس فایل‌ها را با هش محتوا نسخه‌دار می‌کند و لینک ورود در هدر را نیز به نسخهٔ فعلی HTML پنل وصل می‌کند. بنابراین نسخهٔ جدید HTML با CSS/JS قدیمی مرورگر ترکیب نمی‌شود. تغییر فایل‌های وابسته بدون اجرای دوبارهٔ این دستور باعث شکست تست `assets.test.cjs` می‌شود.

## حرکت و جلوه‌های بصری

`admin/motion.js` ذرات نور Canvas و پارالاکس ناحیهٔ لوگو را مدیریت می‌کند. حلقه‌های مداری، درخشش دکمه، شناوری لوگو و کارت‌ها با CSS اجرا می‌شوند. انیمیشن تأیید ورود فقط پس از بررسی موفق حساب و دسترسی مدیر نمایش داده می‌شود. رندر ذرات هنگام مخفی‌شدن پنل یا تب متوقف می‌شود؛ تمام حرکت‌های تزئینی تابع `prefers-reduced-motion` هستند. لینک هدر، HTML و وابستگی‌های پنل با هش محتوا نسخه‌دار می‌شوند.

## امکانات مدیریت محتوا

- پروژه‌ها: افزودن، کپی، حذف، بالا/پایین‌بردن، جست‌وجوی عنوان/دسته/کارفرما، فیلتر دسته و نمایش/عدم‌نمایش در ویترین. پروژهٔ جدید یا کپی‌شده به‌صورت پیش‌فرض مخفی است. **مخفی‌کردن محرمانگی نیست**: JSON محتوا عمومی است و لینک تصویر هم عمومی می‌ماند.
- هویت برند، نام و لوگو، تصویر پروفایل، وضعیت همکاری، تیتر و متن هیرو؛ دربارهٔ استودیو و مزیت‌ها.
- خدمات و خروجی‌ها، مهارت و درصد، آمار با شمارش خودکار آثار قابل‌نمایش، مراحل همکاری و نظرات/امتیازها. مجموعه‌ها قابلیت افزودن، حذف و جابه‌جایی دارند و می‌توانند خالی باشند.
- متن تماس، نشانی، شبکه‌های اجتماعی، پاورقی، عنوان/توضیح SEO و تم اولیه. تم ذخیره‌شدهٔ قبلی بازدیدکننده همچنان اولویت دارد. تنظیمات SEO پس از بارگذاری JS اعمال می‌شوند؛ crawler فاقد JS فقط متای ثابت HTML را می‌بیند.
- کلید میان‌بر Ctrl/Cmd+S برای انتشار. تمام بخش‌ها از قرارداد مشترک `content.js` برای اعتبارسنجی و حذف کلیدهای ناشناخته/احراز هویت استفاده می‌کنند.

## رسانه و نسخه‌های پیشین

Migration `20261029_miim_management.sql` **اعمال شده است؛ دوباره اجرا نشود**:

- bucket مستقل `miim-media`، خواندن عمومی؛ آپلود فقط برای مدیر با RLS. PNG/JPEG/WebP/GIF تا ۵ مگابایت، تشخیص امضای فایل در مرورگر، نام تصادفی و بدون بازنویسی فایل قبلی. هیچ کلید خصوصی برای آپلود در مرورگر نیست.
- آپلود فایل بلافاصله انجام می‌شود ولی تا انتشار، تصویر جدید به سایت متصل نمی‌شود. حذف پروژه/لغو پیش‌نویس یا جایگزینی تصویر فایل قبلی را پاک نمی‌کند؛ فایل‌های بلااستفاده ممکن است باقی بمانند و پاک‌سازی باید جداگانه و با بررسی ارجاع‌ها انجام شود.
- `miim_revisions` با RLS فقط‌خواندنی برای مدیر؛ trigger سرور نسخهٔ قبلی را در هر UPDATE بایگانی کرده و ۳۰ نسخهٔ آخر را نگه می‌دارد. سابقه برای بازدیدکننده عمومی نیست. بازیابی، نسخهٔ جاری انتشار را تغییر نمی‌دهد و تعارض نسخه همچنان بررسی می‌شود.

## پیش‌نویس محلی و پشتیبان

تغییرات **معتبر** پس از حدود ۷۰۰ میلی‌ثانیه در `localStorage` با کلید مجزای شناسهٔ کاربر ذخیره می‌شوند؛ ورود دوباره پیشنهاد بازیابی می‌دهد و هیچ‌وقت خودکار منتشر نمی‌کند. فیلد ناقص/نامعتبر جایگزین آخرین پیش‌نویس معتبر نمی‌شود. مرورگر اشتراکی امن فرض نمی‌شود؛ خروج صریح و انتشار/لغو موفق پیش‌نویس محلی را پاک می‌کنند. محدودیت یا غیرفعال‌بودن storage ممکن است مانع ذخیرهٔ محلی شود؛ از خروجی JSON نیز استفاده کنید.

ورود JSON حداکثر یک مگابایت است، پیش از جایگزینی تأیید و اعتبارسنجی می‌شود و دادهٔ قدیمی با نسخهٔ پایه تکمیل می‌گردد. خروجی و تاریخچه حاوی رمز یا نشست نیستند. فیلد قدیمی Formspree فقط برای سازگاری فایل‌های قدیمی باقی مانده و دیگر مقصد فرم نیست؛ فرم سفارش از سرویس خصوصی روبیکا استفاده می‌کند.

تست مرورگر توسعه‌یافته با SDK واقعی و API شبیه‌سازی‌شده، عملیات پروژه/آپلود، ویرایش هیرو/خدمات/SEO، پیش‌نویس پس از reload، ورود JSON و تاریخچهٔ بدون انتشار و نمایش نتیجه در صفحهٔ عمومی را نیز پوشش می‌دهد. این تست اثبات ارسال ایمیل یا ورود HTTP واقعی به تولید نیست.

## روبیکا و محدودیت انتخاب و درگ محتوا

روبیکا با کلید `rubika` در ویرایشگر شبکه‌های اجتماعی قابل انتخاب است. آیکون `Image/rubika.png` همان فایل ارسالی مالک است؛ پروفایل اولیه `https://rubika.ir/MIIM_DEV` در نسخهٔ پایه و سند ابری (با حفظ سایر فیلدها) ثبت شده است.

فایل `content-guard.js` فقط در صفحهٔ عمومی بارگذاری می‌شود: انتخاب و درگ متن‌ها، لینک‌ها و تصاویر را خارج از فیلدهای قابل ویرایش محدود می‌کند. منوی راست‌کلیک فقط روی تصاویر و قاب‌های آثار مسدود است؛ تصاویر بعد از بارگذاری ابری هم `draggable=false` می‌گیرند. CSS انتخاب متن صفحه را غیرفعال می‌کند ولی input، textarea، select و contenteditable استثنا هستند. CSS منوی لمس طولانی را در مرورگرهای پشتیبان محدود می‌کند. حرکت گالری، فرم سفارش، دکمه‌های اختصاصی کپی اطلاعات تماس، کلیدهای مرورگر و ابزارهای مدیریت مسدود نشده‌اند؛ انتخاب دستی متن اطلاعات تماس مثل سایر متن‌های عمومی محدود است. لینک شبکه‌های اجتماعی نیز پیش از رندر باید پروتکل HTTP/HTTPS معتبر داشته باشد.

**این محدودیت‌ها امنیت کامل یا DRM نیستند.** متن‌ها با ابزارهای توسعه یا غیرفعال‌کردن محدودیت‌ها همچنان قابل کپی‌اند. تصاویر عمومی با لینک مستقیم، ابزارهای توسعه، خاموش‌کردن JS یا اسکرین‌شات همچنان قابل دریافت‌اند. برای آثار حساس از پیش‌نمایش کم‌کیفیت/واترمارک استفاده کنید و فایل اصلی را عمومی نکنید. این تغییر شامل تست نفوذ کامل سایت نیست و جایگزین احراز هویت و RLS سرور نمی‌شود.


## سفارش‌ها و ربات روبیکا (بدون ایمیل سفارش)

ربات مقصد `@miimsite_bot` است. کلید `RUBIKA_BOT_TOKEN` فقط در Edge Function Secrets ثبت می‌شود؛ پنل هرگز توکن را دریافت یا درخواست نمی‌کند. تابع مستقل `miim-rubika` با `verify_jwt=false` منتشر می‌شود، زیرا ثبت سفارش عمومی است؛ **تمام عملیات مدیریت** در خود تابع با `/auth/v1/user` و RPC موجود `miim_is_admin()` سمت سرور احراز هویت و مجوز می‌شوند. خاموش‌بودن verify_jwt به معنی عمومی‌بودن صندوق یا تنظیمات نیست.

### اتصال اولیهٔ پیوی

۱. وارد مدیریت شوید و به «سفارش‌ها و روبیکا» بروید.
۲. «ساخت کد اتصال پیوی» را بزنید؛ یک کد تصادفی یک‌بارمصرف ۱۰دقیقه‌ای نمایش داده می‌شود.
۳. همان کد را با حساب گیرنده در **پیوی** ربات بفرستید (نه گروه و نه پیام فوروارد).
۴. «کد را فرستادم؛ تأیید اتصال» و سپس «ارسال پیام آزمایشی» را بزنید و دریافت واقعی را در روبیکا بررسی کنید.

کد به شناسهٔ مدیر متصل است؛ فقط هش و زمان انقضایش در جدول خصوصی ذخیره می‌شود. سرویس `getUpdates` را صفحه‌بندی کرده و فقط پیام جدیدِ ویرایش‌نشده با کد دقیق از یک چت نوع User را می‌پذیرد؛ کد بعد از اتصال مصرف می‌شود. کد را در چت عمومی منتشر نکنید. پیوی بر اساس «اولین کسی که پیام داده» انتخاب نمی‌شود. Chat ID هم فقط در تنظیمات خصوصی سرور می‌ماند. ربات را با polling/webhook برنامهٔ دیگری به‌طور هم‌زمان استفاده نکنید.

### تحویل و خطا

سفارش با نام، موبایل، ایمیل اختیاری، خدمت، بودجه و شرح پروژه ابتدا در `miim_order_inbox` ذخیره می‌شود، سپس برای ارسال به پیوی تأییدشده تلاش می‌شود. قبل از اتصال ربات یا در قطعی آن، سفارش در صندوق باقی می‌ماند؛ پیام موفقیت فرم میان «ثبت در صندوق» و «تأیید ارسال روبیکا» فرق می‌گذارد. رسید API تضمین خوانده‌شدن توسط انسان نیست.

بخش صندوق ۵۰ سفارش آخر را با وضعیت نشان می‌دهد. در حالت failed/queued می‌توانید ارسال را دوباره امتحان کنید. در timeout، پاسخ نامعتبر یا قطع اجرا، وضعیت ممکن است uncertain/sending بماند؛ **اول پیوی را بررسی کنید**، زیرا تلاش مجدد دستی می‌تواند پیام تکراری ایجاد کند. درخواست مجدد خودکار در این حالت انجام نمی‌شود. sending فقط پس از دو دقیقه با اقدام صریح مدیر دوباره قابل‌ارسال است. بعد از اتصال اولیه، سفارش‌های صف‌شده را نیز از صندوق ارسال کنید؛ cron یا worker پس‌زمینهٔ خودکار وجود ندارد.

UUID درخواست و fingerprint مانع ثبت دوبارهٔ همان تلاش می‌شوند؛ claim اتمیک مانع ارسال هم‌زمان است. frontend تا زمان دریافت پاسخ فرم را قفل می‌کند و در خطا داده‌ها و شناسه را نگه می‌دارد. شناسه پس از reload مرورگر حفظ نمی‌شود؛ ارسال مجدد بعد از reload ممکن است سفارش جدید بسازد.

### امنیت و نگه‌داری

Migration `20261029_miim_rubika.sql` اعمال شده؛ دوباره اجرا نکنید. سه جدول مستقل با RLS بدون مجوز anon/authenticated و دو RPC با دسترسی صرفاً service_role ساخته می‌شوند. اطلاعات IDEA، جدول محتوا، ایمیل یا سیاست احراز هویت تغییر نمی‌کنند. service-role و توکن ربات هرگز به مرورگر فرستاده نمی‌شوند. اطلاعات مشتری با textContent نمایش داده می‌شود و در محتوای عمومی یا بکاپ سایت قرار نمی‌گیرد.

ورودی JSON حداکثر ۱۲KB، فیلدها محدود و اعتبارسنجی‌شده، شمارهٔ ایرانی، honeypot، محدودیت پایدار DB (۳ درخواست/۱۰دقیقه برای IP هش‌شده، ۲ درخواست/۱۰دقیقه برای موبایل و ۳۰ درخواست/ساعت در کل) و قفل تراکنشی برای intake وجود دارد. CORS محدود به `https://miimdev.github.io` است؛ origin به‌تنهایی محافظت ضدبات نیست و امکان جعل آن خارج از مرورگر وجود دارد. پروژه‌های بزرگ‌تر به CAPTCHA و محدودیت لبهٔ شبکه نیاز دارند. `MIIM_ALLOWED_ORIGINS` اختیاری برای دامنه‌های مشخص اضافه است؛ wildcard نگذارید. آی‌پی خام ذخیره نمی‌شود؛ تشخیص IP وابسته به هدرهای مورد اعتماد دروازهٔ Supabase است.

سفارش‌ها و رخدادها بعد از ۹۰ روز هنگام ثبت درخواست جدید پاک می‌شوند؛ این سیاست، حذف زمان‌بندی‌شدهٔ دقیق نیست. پاک‌سازی نسخه‌های پشتیبان دیتابیس تابع سیاست خود Supabase است. داده‌ها همچنین به روبیکا منتقل می‌شوند؛ پیام حریم خصوصی کنار فرم این را اعلام می‌کند.

اعلان مدیریت فعلی شامل **انتشار موفق محتوا از همین پنل** است؛ متن و شمارهٔ نسخه از سرور بررسی می‌شوند و هر نسخه فقط یک تلاش ارسال دارد. قطعی اعلان نتیجهٔ ذخیرهٔ محتوا را عوض نمی‌کند؛ برای اعلان‌های شکست‌خورده retry خودکار وجود ندارد. ورود، رمز، توکن و لینک بازیابی به ربات ارسال نمی‌شوند؛ بازیابی رمز حساب مدیریت همچنان با Auth/ایمیل است. سایر رویدادها هنوز اعلان ندارند.

### آزمون و انتشار

`tests/rubika.test.cjs` منطق edge را با fetch شبیه‌سازی‌شده، بدون توکن واقعی یا ارسال پیام واقعی تست می‌کند. تست مرورگر SDK واقعی را با پاسخ‌های API شبیه‌سازی‌شده استفاده می‌کند. DB زنده برای دسترسی‌ها، محدودیت تعداد، duplicate/claim با تراکنش rollback تست شد؛ سفارش آزمایشی دائمی یا پیوی از طرف توسعه‌دهنده ثبت نشد. فعال‌بودن تابع به معنی اثبات دسترسی شبکهٔ روبیکا یا تحویل واقعی نیست؛ مدیر باید مرحلهٔ پیام آزمایشی بالا را کامل کند.

سورس edge در `supabase/functions/miim-rubika/index.mjs` است و به‌صورت یک باندل مستقل بدون import شبکه‌ای منتشر می‌شود. `npm run build:edge` باندل را در `.cache/miim-rubika-deploy.mjs` می‌سازد؛ فایل خروجی وارد Git نمی‌شود. بعد از هر تغییر backend همان سورس آزموده‌شده را bundle و با connector منتشر کنید؛ build مرورگر به‌تنهایی edge را به‌روز نمی‌کند.
